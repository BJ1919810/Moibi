## 一、完成内容

### R3-a 伏笔与计划/实际拆分

- `outline.foreshadows[].id` 稳定非空；`plantChapter/payoffChapter` 只是计划，不视为剧情发生。
- 章节 `foreshadows[]` 显式引用 ID、动作、批准情况，未经批准的 `pay_off` 不给正文模型真相；`needsReview` 关联不能触发回收。
- `ledger.foreshadowEvents[]` 独立存储真实铺设、强化、回收的章节、正文版本与精确证据位置，只有已确认章节的引文逐字匹配、动作有计划、回收已满足授权时才写入。没有证据则不改变生命周期。
- 从早期已确认的伏笔事件到后续 WriterPacket，可查询并按需释放审核过的 `safeReveal.text`。原始 `payoff` 文本仍属于作者层数据。
- 新增 `makeLinkAssistantPacket()` 及 `importLinkProposals()`：模型建议只作为 `needsReview` 候选；需要显式 `reviewed=true` 和审核身份，才能批准关联。字符串近似只能做候选排序，**不能自动确认**。

### R3-b 旧作品可信恢复

- 已确认第 1、2 章正文原样保留。
- 原有 10 条旧摘要事实、14 条旧线索保留在隔离区，直到有可核对的正文证据。原始自然语言提取是“摘要/推断”，不能凭词语相似度授予权威状态。
- 通过逐字引文恢复了 5 条可追溯的正文观察事实；每条携带 `sourceChapter`、`sourceSpan.start/end/quote` 与 `sourceVersion`。没有强迫把小说一句话解释成现实真相。
- `recovery.js` 支持精确匹配旧记录；人工核准的语义恢复候选；以及在 R2 状态引擎中恢复已核实的状态、角色认知（模型候选默认隔离）。
- 自动运行不会把第 3—34 章大纲当成已经发生的事情。

### R3-c 权限与披露

- 角色隐私采用 `entity.revealProjections[]` 中已审核的 `safeText`，章节 `reveals[]` 必须授权且满足事件前置条件；不直接把 `entity.secret` 整块给正文模型。
- 伏笔 `pay_off` 需要：明确的章计划、章号对应、`approved`、`linkStatus != needsReview`、前置事件、历史铺设事件，以及已审核 `safeReveal`。未满足时阻断编译，不允许模型自行推断。
- `readerKnownProjections()` 支持已正式揭示的事实在后续章节继续出现，但**不会自动让所有角色也知道**。
- `writerSummary/writerGoal` 必须获得 `writerTaskApproval='author-approved'` 才能发送给正文。旧大纲未经过安全投影的完整章节概要继续保留给规划层，正文得到保守任务回退并显示 `diagnostics.taskStatus='safe-fallback'`。
- 确定性泄漏检查只能覆盖已知明文泄漏；**无法数学保证检测全部语义等价的泄漏**，因此增加输入白名单与未授权阻断，不以词表检查当作唯一屏障。

## 三、操作说明

在 `mobi/` 目录：

```bash
npm test
node scripts/r3-upgrade.mjs p_64d57c208eb4
# 可选：配置好 API Key 后，显式调用一次规划模型提出候选（会计费），不自动确认：
node scripts/r3-upgrade.mjs p_64d57c208eb4 --assist
# 把待审核 proposal 编辑核实后，可显式审核关联：
node scripts/r3-upgrade.mjs p_64d57c208eb4 --approve review.json --reviewer owner
```

工具会生成 `docs/R3_迁移与待审核清单_p_64d57c208eb4.json`；首次变更前备份 `data/projects/<id>.pre-r3.bak`（交付 zip 不含此备份，包内已有完成迁移的作品）。

候选 JSON：

```json
{"links":[{"foreshadowId":"fs_...","plantChapter":10,"payoffChapter":26,"evidence":"经核对的章计划理由","confidence":0.85}]}
```

人工核验前不要设置 `reviewed` / `approved`。批准伏笔回收前需建立历史已确认的铺设事件，并为真相准备经审核的 `safeReveal`；不能仅因为到达了第 26 章就解锁。

## 四、已知未完成项（属于 R4/R5 或需要作者批准）

- R4：现在 `pipeline.generateChapter()` 仍沿用旧 `status=committed` 行为，没有正式的草稿/审批事务与任务幂等。R3 的证据和披露逻辑提供了门禁，但不代表整章提交一致性已经完全闭环。
- R5：仍未实现依据显式事实依赖和 token 预算的动态上下文编译，以及写作前的 L2 章节任务安全重规划。超过预算的记录暂靠诊断报告，不是完整 L2 检索。
- 旧作品作者侧全文大纲（尤其第 26 章）需要完成伏笔关联的语义审核才能真实验证远程回收；本次只生成候选并如实标注未完成。
- 当前旧章节 `writerSummary/writerGoal` 缺人工授权，所以会使用较保守的安全任务，剧情细节不足，需要在后续 L2 补充安全任务。优先防止秘密注入，而非冒险直接透传作者侧概要。
- 语义状态/认知恢复需要已核对的逐字证据和显式审核，不会为了凑数量伪造记录。

## 五、必测用例

1. 有计划但正文没出现：不得标记 planted。
2. 没有铺设事件，或前置事件缺失：不得在第 26 章揭示。
3. 已铺设、有审核许可且有安全投影：可以披露，同时原始 `payoff`、`secret` 不随意进入正文。
4. 已确认的读者真相延续到后续章，但角色认知不自动改变。
5. 模型建议的历史关联仍处于 `needsReview`，不直接升级权威信息。
6. 旧事实与正文精确吻合方可升级，未审核的语义提取继续隔离。
7. 迁移重复执行不产生重复事件、正文不发生变化。

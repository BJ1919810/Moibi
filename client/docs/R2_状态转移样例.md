# R2 状态转移 · 数据样例

> 本文件由 `mobi/scripts/demo-state-transitions.mjs` 生成，不是手写的说明。
> 每个场景都会打印**转移前**与**转移后**的账本真实内容。

## 0. 取材

- 基底：真实作品《十年雨信》，读自 `data/projects/`
- 真实规模：实体 6 个 · 已写章节 2 章 · 全书规划 34 章
- 真实账本：事实 10 条 · 线索 14 条 · **状态 0 条 · 认知 0 条 · 事件 0 条**

**这一点必须先说清楚**：真实旧作品里**一条状态记录都没有**。
原因是 v1 的数据结构里只有 `state.facts / state.threads / state.lastSummary`，
压根没有「当前状态」与「角色认知」的槽位 —— 不是迁移弄丢了，是原来就没有。
所以下面所有状态转移都是**在真实实体与真实线索上驱动的**，
转移序列每一步都注明依据；依据来自正文/线索的会写明出处，其余标注「人工构造」。

## 场景 A · 同一章内往返（档案馆 → 青江桥 → 档案馆）

依据：真实线索「沈砚计划下班后去青江桥」，以及信中说「林晚三天后会死在青江桥下」。
同一章里他先去了又回来，是长篇里非常常见的情形。

**要求**：三次变化 = 三条记录、三个事件，两次「档案馆」必须各自可追溯。

## 场景 B · 跨章转移，以及「第 N 章时他在哪」的回查

依据：线索「沈砚计划下班后去青江桥」→ 第 4 章他回到馆里查尾号零七档案。
要求：**查指定章节的有效状态，而不是最新状态**。

第 4 章转移之后，逐章回查同一主体同一属性：

| 查询章 | 该章有效取值 | 该记录当前状态 |
|---|---|---|
| 第 2 章 | （尚无记录） | — |
| 第 3 章 | 青江桥 | superseded |
| 第 4 章 | 档案馆修复室 | active |
| 第 5 章 | 档案馆修复室 | active |

完整轨迹（`queryStateTimeline`，含已被替代的历史）：

| state_id | 主体 | 属性 | 取值 | 生效章 | 失效章 | 状态 |
|---|---|---|---|---|---|---|
| `st_17c4708ddc` | 沈砚 | 所在 | 青江桥 | 3 | 4 | superseded |
| `st_14cdd9f07a` | 沈砚 | 所在 | 档案馆修复室 | 4 | — | **active** |

- 第 3 章查到的是「青江桥」，不是最新的「档案馆修复室」——回查没有被最新值覆盖。
- 但同一条记录的状态是 `superseded`：**存储层留档，查询层按章判定**，两者不冲突。

## 场景 C · 认知演变（suspects → believes → knows），历史必须保留

依据：真实线索「尾号零七档案封皮内侧有一行铅笔字，顾行舟已拍照，待给沈砚看」。
顾行舟对「这卷档案有问题」的把握，是逐步升级的 —— 不是一次跳到位。

完整演变（`queryKnowledgeHistory`）：

| kn_id | 角色 | 内容 | 信念 | 生效章 | 状态 |
|---|---|---|---|---|---|
| `kn_2a30e3642f` | 顾行舟 | 尾号零七档案与十年前的青江桥有关 | suspects | 3 | superseded |
| `kn_e68517aaa0` | 顾行舟 | 尾号零七档案与十年前的青江桥有关 | believes | 5 | superseded |
| `kn_fa49b8edd7` | 顾行舟 | 尾号零七档案与十年前的青江桥有关 | knows | 8 | **active** |

第 6 章时他的认知（`queryKnowledgeAt`）：

| kn_id | 角色 | 内容 | 信念 | 生效章 | 状态 |

一次转移的完整事件：

## 场景 D · 失败保护：一批里有一项非法，整批一条都不落

构造方式：第 5 章已确立「沈砚·所在 = 青江桥」，随后一批标注为第 3 章，
其中第三项要写「沈砚·所在 = 档案馆」—— 时间倒退，属 error 级违规。
**要求**：前两项合法，但整批必须一起放弃；账本必须与本批之前逐字一致。

本批提交返回：

```json
{
  "ok": false,
  "rejected": true,
  "applied": {
    "states": 0,
    "knowledge": 0,
    "events": 0,
    "superseded": 0
  },
  "violations": [
    {
      "code": "time-regression",
      "severity": "error",
      "index": 2,
      "message": "状态时间倒退：第 3 章的新状态早于第 5 章的既有状态（青江桥）"
    }
  ]
}
```

账本计数对比：

|  | 本批之前 | 本批之后 |
|---|---|---|
| 状态记录 | 1 | 1 |
| 认知记录 | 0 | 0 |
| 状态事件 | 1 | 1 |

- 账本逐字一致（`JSON.stringify` 比较）：`是`
- 前两项 `宋瓷·所在` 与 `顾行舟·持有` 虽然合法，但一条都没落 —— 整组不得部分生效。

## 场景 E · 重复提交：同一批内容执行两次，结果与执行一次完全一致

构造方式：同一提交标识（batchKey）连续执行两次。
**要求**：第二次不得产生任何新记录、新事件；也不能因为「内容相同」把新的一次真实变化误判成重复。

两次执行对比：

|  | 第一次 | 第二次 |
|---|---|---|
| ok | true | true |
| skipped | false | true |
| skip 原因 | — | duplicate-batch |
| 新增状态 | 1 | 0 |
| 新增认知 | 1 | 0 |
| 新增事件 | 2 | 0 |

- 第二次执行后账本与第一次逐字一致：`是`

**反面**：换一个提交标识、内容完全相同 —— 必须当成新的一次真实变化。

|  | 第二次（同标识） | 第三次（新标识） |
|---|---|---|
| skipped | true | false |
| 新增状态 | 0 | 1 |
| 新增事件 | 0 | 2 |


## 场景 F · 证据溯源：从一条状态回到正文版本与位置

要求：状态事件能关联**来源正文版本**与**具体位置**。
R2 已把 `sourceChapter / sourceVersion / sourceSpan` 贯通到记录与事件；
`sourceSpan`（正文内的具体位置）留待反向提取补，本样例如实显示为未填。

从状态记录反查：

```json
{
  "state_id": "st_17c4708ddc",
  "event_id": "ev_a1630d43d6",
  "sourceChapter": 3,
  "sourceVersion": 3,
  "sourceSpan": null,
  "batchKey": "ch3:cf_7be2f1a90c",
  "idempotencyKey": "ik_8b6c454898"
}
```

从事件正查：

| event_id | 来源章 | 正文版本 | 正文位置 | 提交标识 |
|---|---|---|---|---|
| `ev_a1630d43d6` | 3 | 3 | — | `ch3:cf_7be2f1a90c` |


### 三个 ID 各司其职（同一个场景里的实际取值）

| ID 类型 | 标识什么 | 本场景取值 |
|---|---|---|
| `state_id` | 一条状态记录（当前是什么） | `st_17c4708ddc` |
| `event_id` | 一次状态转移（发生了什么） | `ev_a1630d43d6` |
| `idempotency_key` | 一次提交（是不是重复） | `ik_8b6c454898` |

## 汇总

| 场景 | 要求 | 本样例中的结果 |
|---|---|---|
| A 同章往返 | 允许再次进入同一状态，且两次可区分 | 3 条记录 / 3 个事件，末条 active |
| B 时间回查 | 能查指定章节的有效状态 | 第 3 章 → `青江桥`，不受第 4 章影响 |
| C 认知演变 | 保留变化历史，当前认知正确 | 3 条留档，上下文只取 1 条 |
| D 失败保护 | 非法转移不得部分生效 | 整批拒绝，账本逐字未变 |
| E 重复提交 | 重复提交不重复执行 | 第二次新增 0；换提交标识则照常生效 |
| F 证据溯源 | 关联来源正文版本与位置 | sourceChapter / sourceVersion / batchKey 已贯通 |
| G 旧数据补齐 | 确定性、可重复、不伪造证据 | 同键 3 条 active 收尾为 1 条，fromValue 留空 |


> 本样例全部由 `server/state-engine.js` 的公开接口驱动，与该引擎在生成流水线里
> 被调用的路径完全一致（`ledger.applyExtraction` → `applyStateChanges`）。
